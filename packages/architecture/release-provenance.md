# Check a release's contents and source records

Use this method when a release has licence, notice, origin or source-delivery requirements. Identify candidate digest, build inputs, output artifacts, proposed uses and recipients. Distinguish reviewed working files, committed source, built bytes and distribution destination.

Inventory what the recipient will receive or use. Connect source and artifact inventories through observed build or packaging, including inherited, vendored, generated and embedded material. Identify components by source path and version and by the artifact containing them. A package name, language or root declaration alone does not establish a shared component. Mark included, excluded and unknown membership separately. Compare manifests, file headers, notices, credits, licence text and generated metadata. Locate conflicting declarations by path and preserve superseded observations in the existing release records.

Generate inventories from the release inputs when assembling the release and attach them to its build or release artifacts. Keep the declarations and generator in source control; do not commit generated inventories as another maintained source. This does not change retention of original notices or the historical release records readers still need.

## Check dependency intake for the selected profile

Fix source revision, resolver inputs, target, build profile, features and packaging route. Compare declared dependencies and the resolved bill of materials with what the build compiles, bundles, downloads or uses at runtime. Include transitive dependencies, optional branches, build scripts, native libraries, generated and vendored material and services. Distinguish build-only, test-only, shipped and runtime-only membership. Unknown inclusion remains open until that route is observed.

For models or data, identify weights, tokenizers, datasets and evaluation inputs consumed or distributed, their versions and separate terms. State origin information the supplier withholds. Hosted services need their own scope and terms. Give the rights owner component and proposed-use facts, licence and notice bytes and unresolved items. Technical compatibility, permission to use and owner acceptance are separate conclusions.

Run a clean resolution or build for this profile. Change a feature or target as a control when it affects membership. Compare lock, build or packaging trace and delivered contents for the candidate. Report which observations establish resolution, inclusion and runtime use. Resolve missing or ambiguous facts with their owner before adopting the affected dependency.

### Check generated inventory against its selected inputs

Identify source inventories, notices and artifact inventories required for delivery. For each generated source inventory, fix generator and toolchain revisions, locks and digests, retained inputs and any fixed timestamp or ordering rules. Regenerate in isolation and use the owning checker to compare bytes with saved output. Keep unresolved declarations and each inventory's scope visible.

Test changed input under an old pin and changed or missing output under original inputs. Distinguish rejected inputs from valid inputs with stale output. Confirm checking does not alter evidence files. Reconcile changed inputs before updating pins or regenerating saved results.

Identify final artifacts and archive members separately. Associate each scan with the bytes, tool and scope it examined. Compare with the assembled package, including files alongside a scanned binary. Source inventory, binary scan and delivered package answer different membership questions. Send unresolved terms and delivery duties to their owners.

## Reconcile inherited material against the exact fork

Fix the candidate tree and claimed inherited revisions. Distinguish direct fork base, transitive sources and selected build dependencies. Compare membership and object identity across each relationship. Classify unchanged, moved, modified, added, removed and unresolved material; compare with the proposed notice and actual release. A new path can contain inherited bytes. Modification or generation does not automatically remove inherited obligations.

Verify claimed local additions exist in the candidate. An absent path, placeholder or generated asset with unknown source is a discrepancy when described as delivered work. Compare inherited notices and exclusions with included material. Keep source and output identities, ancestry, supplied contributor or permission records, build inputs and unresolved material in the release inventory. File equality establishes neither authorship nor ownership or permission.

Give the named rights owner an inventory and supporting records identified by their content digest. Keep acceptance separate and tied to those records, candidate, proposed action, conditions and decision-maker. Reopen affected findings when candidate, use or support changes. Test a moved inherited file misclassified as an addition, missing or placeholder addition, generated dependency of unknown origin and acceptance covering another candidate or action. Report technical findings and the remaining rights decision separately.

## Hand off evidence and verify delivery

Supply components, declared terms, contributor or upstream records, proposed actions and unresolved items to the rights owner. Inventories and scanners reveal gaps; they cannot settle ownership, controlling terms or permission. Record notice, source and other delivery obligations only once the responsible authority establishes them for this candidate and action.

For required source delivery or offers, identify advertised location, recipient, source revision and released artifact. With permission, test access equivalent to the recipient's and verify matching source. A URL, metadata declaration or archive alone does not prove the recipient can obtain it. Distinguish notice placement, source correspondence, owner acceptance and dispatch. Leave missing or unverified members open and report the observation or decision required before release.
