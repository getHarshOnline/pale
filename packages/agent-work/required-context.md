# Keep required context visible

Identify the decision, subject, recipient and scope before collecting context. In the handoff, name each required source's role, the owner who selects it, its reference or revision, permitted audience and the decision it supports. Work out these requirements independently of a builder's optional attachments or draft. Optional material can add evidence within the same scope; required source roles and disclosure limits still apply.

## Check what reaches the recipient

Check required sources when preparing the handoff and again when the author or reviewer receives it. Keep owner instructions, candidate material and independent evidence distinct. Selecting a source, capturing it and observing that the recipient saw it are different facts. When one artifact serves several roles, show each role and which evidence each recipient actually received.

A missing, stale, denied or oversized required input holds the dependent decision, unless an explicitly permitted narrower task can proceed. In the handoff, say which source role is missing and whose answer or evidence can resolve it. Judge a smaller input against the work it still supports.

Test removal of every optional input, removal of one required source, a reference selected by the wrong owner and an insufficient context budget. Required roles must survive optional omissions, and a missing required source must remain visible to the recipient.

## Recheck context when dependent work uses it

Associate the handoff with the chosen revision and exact delivered bytes. Follow the source owner's rules for freshness and permission, including purpose, expiry, dependencies and revocation. Recheck at use when work can wait or permission can change after acceptance. An earlier read establishes what was delivered then; current use needs current permission and sufficiently fresh inputs.

If context becomes unavailable or invalid, stop the dependent use or use a separately permitted narrower variant. A refresh that changes the evidence needs a newly accepted association with the task before work resumes. Keep the original handoff and earlier use records according to the owner's retention policy. Reconcile any action or disclosure that already occurred through its owner.

Rehearse a handoff delayed past expiry or revocation, one still valid, and a refresh producing new bytes. Check that the old handoff cannot silently acquire replacement bytes, that the newly accepted handoff can proceed, and that each use identifies its actual content and permission.

## Distinguish missing content from missing permission records

For each handoff variant, name its required context, the policy permitting it and the approval or acceptance records required before dispatch. Match those records to the owner, task, recipient and current handoff. Give any fallback its own scope and expiry.

An owner may permit a reduced task that omits a named source under stated conditions. It must still obtain and check every acceptance record that this variant requires. If a supporting service cannot issue one, stop that path. Partial content still needs its ordinary read and task-association checks, with its reduced coverage visible.

A task variant that needs no context from that service must be explicitly classified and permitted on its own. Failure of the assisted path cannot grant that permission. Check that the valid independent path runs without contacting the unavailable service.

Test the full and allowed reduced variants separately. Remove a source while the acceptance service is available, then withhold each required acceptance record. Try a record from another handoff or an expired generation. In the review, say where dispatch stopped, which narrower result could proceed, and whether a later use record was actually required. Keep preparation, acceptance, dispatch and observed use distinct.
