# Do the agreed work and check its result

Start from the authorised request and the current target. Know the outcome, owner, source version, permitted reads and changes, protected files or systems, required checks, any budget and what ends the task. Use the existing request or task record for this; an ordinary change needs no separate planning file. Access shows what a tool can reach, while the request and its owner's permissions define what you may do.

## Keep the change within the request

Read the current target before changing it and distinguish existing work from your own edits. Keep a colleague's unrelated changes. Resolve a conflict rather than discarding, normalising, publishing or reinterpreting another owner's state to make your implementation easier. If the work needs a change outside its agreed repository, data, policy, publication or financial scope, prepare that change for its owner and continue what is already authorised.

Analysis, proposals, local edits, external messages, release, activation and irreversible actions have different consequences. Use permission already given for the relevant action; do not ask again or infer wider permission from it. Keep a recovery path proportionate to the consequence. If the intended target cannot be identified, resolve it before acting instead of substituting a wildcard, broader destination or remembered state.

## Say what the check establishes

Inspect the result and run checks that exercise what would fail if the change were wrong. In the reply, distinguish what you inspected, ran, observed, read back or inferred, and name anything unavailable. A focused check establishes the behaviour it exercised; broader claims need broader evidence. Change an assertion, threshold, fixture or review scope only when it is wrong for the intended behaviour, never just to get a pass. Where independent acceptance is required, the judgment that produced the change cannot also approve it.

Return what changed, what the checks showed, failures or remaining risks, and any action needed from the owner. Useful findings belong on the changed page, in the code or in its maintained tests; a task reply need not create another record. A system's required run records stay part of that system. Finish when the agreed result and relevant checks are complete, without turning a successful run into permission for another action.

## Worked example

The request is to correct a guide and run its repository check. Read the current file, keep a colleague's nearby edits and correct the requested part. Run the guide check and report what it exercised. If the correction also needs a publishing setting in another repository, give its owner the path and proposed change, with any permission already given.

## Before handing off

- [ ] Is the agreed result complete within its existing permission, with other people’s work preserved?
- [ ] Do the checks exercise what could fail, and does each claim match what was actually observed?
- [ ] Are remaining failures, uncertainty and the owner’s next action clear in the result’s proper home?
