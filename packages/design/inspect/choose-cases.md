# Choose the cases that can answer a rendered question

## Choose the claims and conditions

Bind the actual build, routes, audience tasks, selected identity and review platform. Enumerate affected page families by task and structure. A route crawl proves reachability, a component capture proves that component, and a complete page shows composition. None establishes all the others. Include generated and opened surfaces through their invoking journey.

Choose conditions from the local contract and change risk, including every previously failing case. Honor an explicit exhaustive scope. Otherwise use representative complete processes and relevant combinations, with unrun cells visible. Do not turn every small repair into a full-site campaign.

Treat supported light/dark and full/reduced motion presentations as authored renditions. Preserve the intended emphasis and state comprehension when the carrier changes from motion to type, material, light or composition. Check explicit preference, system-following preference and the unsaved default separately where offered. A dark-looking identity is not evidence that dark preference works.

Capability loss is another axis: scripts, graphics, fonts, forced colors and other supported fallback conditions. The underlying content, source qualifications, navigation and held state must remain useful. Context is the reader's task and input situation, not width alone. Recompose the shared content and state for the available space and inputs, keeping any necessary variants synchronized. A contextual convenience cannot be the sole path to a fact or destination; a mobile-only copy must not silently diverge from the shared payload.

## Choose cases where two changes can interact

| Case | What it can expose |
| --- | --- |
| Default, explicit color choice and system preference | A stored default can differ from the system path. Compare the resolved values and first paint. |
| Narrow, dark and reduced together | A cropped label, weakened contrast or missing state can disappear only in the combination. |
| Script, font or graphics failure in a real task | A fallback may be present while the visible action or meaning is lost. |
| Keyboard and pointer at two useful widths | Focus and reachability can diverge from what the pointer or screenshot suggests. |
| A changed shared component across its consumers | One wrapper, template or identity override can retain the earlier behavior. |
| The matching moment in a reconstruction | An opening can match while the transition, interruption, return or end has drifted. |

Name the routes, widths, preferences and inputs actually run. Keep the ones still open visible when a device, font, provider or reference state is missing. A crawl shows reachability. A rendered still shows the frame. Exercise an interaction or watch a transition to judge that behavior.

## Worked example

A changed menu appears on article, index and search pages. Open it on the page where the defect occurred, then pick the other consumer with the same shell and the one with a different overlay. Check explicit and system dark if the shell changed them. A route crawl helps find the pages. It cannot show focus return or whether the menu covers the current item.
