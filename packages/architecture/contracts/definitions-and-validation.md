# Check the definition and validation used by a consumer

Use these checks for imported definitions, generated contracts and validation coverage. Keep repeatable cases in the consumer's tests and put the observed inputs, results and gaps in the review reply.

## Check shared definitions in the consumer’s load order

Identify the entry point and the complete ordered set of definitions it imports. Resolve each to its owner, revision and bytes. Files present in a checkout may differ from those loaded. Check transitive imports and namespaces, including competing providers and permitted overrides.

Load that set in a clean run of the actual tool. Exercise different uses of shared names within the same consumer. Compare behaviour, expansion or rendered output with independent expectations for each name. Separate provider tests or a successful build do not establish that combined names preserve their meanings.

Substitute a known conflicting definition. Require rejection, or a behavioural mismatch if the tool permits shadowing. Where overrides are supported, include a control that builds successfully using the wrong definition. Recheck affected consumer routes. Report build completion and resolved behaviour separately from whether the underlying claim is correct.

### Verify input provenance when outputs match

When an import can come from several locations, inspect ordered search roots and paths the tool actually resolved. Use dependency listings, read traces or another independent observation. Identify the source revision and input digest for each path, and retain command and tool version in existing build or test output. A dependency declaration, logical import name or output digest does not reveal which checkout supplied the definition.

Run with the intended input, then place an equivalent copy in another permitted search root. Compare output and resolved inputs separately. Equal output may establish equivalence at that output while the wrong source still violates the required pin. Refuse or report the input source as unresolved if it cannot be identified. The project defines accepted roots and revisions.

## Verify generated contracts at the consumer boundary

Identify the governing definition, declared families, generator and options. Associate generated output with those inputs. Check that the bundle contains exactly the declared families, all references resolve within its dependencies and regeneration matches the checked or packaged artifact. Reproduce output in an isolated directory. Alter a generated byte and omit a declared member to show the freshness and completeness checks detect both failures.

Load the artifact through the real consumer and intended version. Schema validators, SDK bindings, decoders and semantic checks may enforce different rules. Run positive and negative cases through every path covered by the compatibility claim. Report skipped format or reference checks. For signed records, preserve canonical bytes and compare identity and rejection at the actual verifier. Inspect what a packaged consumer ships and loads, as well as what the generator produced.

Use the [validation coverage procedure](../validation.md#verify-which-validation-checks-ran) to establish which checks actually ran. In the review, identify the source, inventory, generator, artifact and consumer, their comparison results and rejection coverage. Keep freshness, wire compatibility, semantic acceptance and deployment as separate conclusions.

## Verify which validation checks ran

Start with the owner's required checks for the artifact versions, entry point and mode. Each check needs eligible inputs, an assertion and an expected result. Inspect discovery, parsing, dispatch and outcome separately for each family. A listed file, schema or test name does not prove an assertion executed. If selection is empty, establish that the eligible scope really was empty.

Use an unchanged valid fixture and a well-formed single violation for each rule tested. Verify that the result identifies the intended check. Also test a malformed prerequisite, missing dispatch and early-stage failure. Mark later checks unobserved if execution never reached them. Rejection elsewhere does not prove the intended assertion caught its violation.

Compare required checks with actual outcomes before accepting the result. Distinguish passed, failed, blocked, unimplemented and intentionally excluded checks. If development mode permits open items, list what remains and compare the same input in strict mode. A passing subset supports only its covered claims. Strict acceptance needs an observed result for every required check under the approved policy. An approved exception changes requirements; it does not supply evidence that the waived check passed. Semantic review and release approval remain separate.

### Reconcile changes to the required check inventory

Identify the previously approved and proposed inventories separately from checker output. Compare stable check identities and meanings: scope, input selector, expected-answer source and whether failure blocks progress. Map renamed, narrowed, split and merged obligations explicitly. Changing the list can improve the verdict without improving the candidate.

For every changed or missing obligation, explain what happened and why in the inventory change review. Distinguish satisfied, superseded, deferred and retired requirements. Satisfaction needs its own proof or accepted review. Narrowing or retirement needs the owner's decision and a visible coverage change. Associate the successor policy and each decision with the artifact, mode and intended release. Preserve the last approved scope and historical results.

Test an approved inventory change and a negative control that silently drops or narrows a required row. Compare the checker's verdict with an independent inventory comparison. Passing an empty or altered list does not resolve the earlier obligation. Stop if the predecessor, mapping or decision cannot be verified. Report old and new scope, support for each change and the acceptance requirement still unresolved.

## Worked example

Two profile builds produce equal output, but one resolved an older shared definition. Compare their actual input trees, load order and generator results. Remove a required validator from a test run and check that the result identifies the missing check even if code still emits.
