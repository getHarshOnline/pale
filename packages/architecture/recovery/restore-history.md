# Recover historical records and their references

Find the earlier record and what it actually linked to. Keep original records intact; report tested paths, versions, reader modes and unresolved recovery claims in the existing recovery review.

## Check historical evidence

If an outcome record depends on exact bytes, associate it with an immutable revision and digest under the owner's retention rules. A mutable view may point to the latest version. Test that the older record still resolves after the view changes, including a move of the storage location.

For each required artifact, read preserved bytes or rebuild from the exact saved inputs, configuration and tool revision. Compare the result with the original digest. Identify whether recovery used retained bytes or a verified rebuild, or produced different bytes or no result. If exact reproduction is impossible, retain the original while policy permits and a claim depends on it. Leave the claim unproved when required bytes cannot be recovered. A digest match establishes content identity; possession history, rights and permission to use restored state need separate checks.

## Resolve historical bytes after a locator is reused

Preserve the original outcome record and locator. Use an owner-approved recovery mapping from that record, artifact role and expected digest to a saved file, object revision or archive member. Several records may share a locator yet require different bytes. Follow the route as a reader would and verify the original digest. Check every referenced artifact needed by the claim, including nested references in scope.

Test two historical versions at the same former locator, plus a moved or missing saved copy. Supply the current view and the other record's version as substitution controls. A reachable path or plausible title establishes navigation, not historical identity. If the required artifact cannot be found among permitted holdings, report the missing proof and preserve the original record for follow-up.

## Verify recovered references from their original base

Identify the referring revision, original member path and base namespace, and saved archive or source version. Moving a document can preserve its text while changing relative links. Recover its original base from the owner's records and resolve only within permitted members. For cross-namespace links, use that namespace's separately pinned inventory and mapping. A matching basename does not identify the target.

Verify the file or member before its exact fragment or declaration. Apply the actual reader's identifier rules, including supported explicit anchors, punctuation, duplicate headings and encoded fragments. A source heading, rendered ID and observed navigation establish different things. For a rendered reading route, inspect output or use the reader's resolver. Confirm the intended section and revision opens despite another destination with the same label.

Keep original bytes and locators. Put current navigation corrections or alternate owner routes in an existing maintained index or patch. For a recovered patch chain, verify the base and patch order, then inspect the restored document and target section. State which historical defects remain. Test a correct file with the wrong fragment, relocated base and unavailable or ambiguous target. Report verified paths, versions and reader modes alongside gaps.

## Check metadata provenance during restore

Identify the original occurrence, carrier bytes, restore tool and options, destination filesystem and metadata needed by the claim. Inventory paths, file kinds, content and required metadata separately. For each field, say whether the carrier stores it and whether restoration matches, changes, omits or leaves it unverified. Inspect metadata on the restored filesystem. An archive listing, content digest or successful extraction does not establish filesystem equivalence.

Separate metadata captured at source from values introduced by packaging, transport, extraction or destination. Attribute a cause only with evidence, such as encoded metadata or a controlled comparison varying the restore route. Test identical content with missing or changed metadata, then a route preserving the required field. Never invent origin or security attributes to make a historical comparison pass.

Report the outcome for every required field and dependent use. Matching content may suffice for a content-only reader. If another reader needs metadata the carrier cannot recover, retain the original occurrence under its owner's rules. A verified custody record can preserve an observation when the owner accepts that form of evidence. Keep separately captured transcripts and review state when the carrier holds only source members.

## Worked example

A report's old locator now returns a new version. Resolve its historical identity, read the saved bytes and reconstruct relative links from the original base. Compare linked material and authorship metadata with what the earlier report actually establishes.
