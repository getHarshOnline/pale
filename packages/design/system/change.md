# Carry a design decision from brief to rendered work

Begin with the request, accepted design and content. A repair keeps the unaffected choices. A new direction needs the sources that bear on the decision. Name what the reader should understand or do in a sentence. Decide where the main emphasis sits and how it changes across a visit. Sketch the opening composition and the relationship between the subject and controls before polishing the details.

Write down only the decisions the work reaches. Record the type voices and reading plane, material and light, motion or input response, and the relevant presentation states. For a new figure choose how it carries the claim. For a sequence sketch its beats, transitions and resting frames. Keep the important no-script or reduced form usable. Ask someone to read a sketch or simple animatic while a fundamental choice is still cheap to change. An existing clear design need not repeat that step.

Read the owning method and project references when taking each decision. Use the system's roles for shared UI values. Put a missing shared role with its owner. A film or other authored scene can keep its own timing and geometry when those express its chosen composition. Preserve a working mechanism where replacing it loses the desired behavior.

Check the changed source and build in the project. Then open the result through the actual reader journey. Compare the pages, input and states the change reaches. Look at the result at its normal scale and inspect the transition or failure in motion when relevant. Passing source checks, working browser paths, and a strong visual treatment answer separate questions. Fix a rendering fault in the build or implementation. When the browser is behaving as designed and the result is weak, fix the design choice. Update the shared system only if the defect belongs there.

## Resume at the decision that is actually open

Read the request, corrections and existing approvals before starting new exploration. A repair can preserve the brief, board, token roles and content while changing one field, recipe or interaction. If direction is open, use a brief and small competing sketches or an animatic to settle it before full production. A project can approve temporary assets for assembly while leaving their final treatment and delivery open. Report the claims that depend on those assets and keep checking independent layout and interaction work.

Before building, write the experience in one sentence. Name the audience, place or material, the useful change and the intended task. Sketch the opening, how attention moves, where emphasis belongs and the reachable next step. Use the same references across the sketch and rendered check. When a need recurs across projects, put the method with the shared concept, token or component. Keep project-specific decisions with the project, and engine behavior with the tool that implements it.

A plan can become a useful prototype without becoming a second specification. Check a prototype's actual limitations and make clear which decisions it can support. Separate implementation, verification and the decision to approve. A locally completed action, such as preparing a request or rendering an artifact, should use the same name in the interface and its review.

## Choose the stage by its unresolved dependency

Use only the stages the request needs. This table describes what each contributes; it does not require a fresh approval or artifact for a decision already settled.

| Work | Begin when | Result the next work can use |
| --- | --- | --- |
| Setup | Authorized execution needs an unverified capability or missing location | Observed readiness for the selected route, with relevant gaps named |
| Intake | Intent leaves a material question open | A grounded brief with assumptions distinguished from supplied decisions |
| Reference board | Direction is open and the brief gives a basis for comparison | Selected and annotated sources in their actual roles |
| Alternative treatments | A useful creative choice needs comparable trials | Candidates that answer a specific unresolved question |
| Direction | Identity or recurring treatment remains open | The applicable identity brief, shared treatment and role choices |
| Production | Direction and sources are sufficient for the requested output | Checked assets or authored scenes for the destination |
| Build | Selected or explicitly provisional material can be assembled | Rendered work checked through its reader journey |
| Release | The output is qualified and the requested release is authorized | The delivered derivative and observation of the actual destination |

Return to the stage that owns a failed result. If every trial misses the brief, revisit the sources or direction; if one crop fails, repair that crop without restarting intake. Record why the attempt failed in the existing project record. While a reserved choice is open, continue work that does not depend on it. Mark a speculative assembly as provisional, while preserving the settled status of unrelated work.

Treat the source library and production workspace as responsibilities, not mandatory folder names. Keep originals and selected masters with their owner; keep editable compositions, decisions and reproducible steps in the project's working home. A renderer's local media copy should point to its source revision or hash and remain replaceable. Check pending jobs in the tool's own records before starting duplicates: a session may have stopped before updating the project's status. A hash identifies bytes; it does not turn an agent's summary into the owner's original request.

Finish with the result and remaining dependencies in the project's existing homes. Keep useful production inputs and selected evidence, and remove disposable working output under the project's retention rules when its consumers are accounted for. A successful export, an accepted design and an observed publication are separate facts. A new destination needs its own applicable output checks and only the additional authority it actually requires.

## Worked example

A reading page's figure now needs a two-state comparison. Keep the existing type, path and document structure. Sketch the figure and its caption. Read the figure's source and keep both units and the qualification in each state. Use the shared focus role and choose a transition that does not move the caption. Build it, enter through the ordinary reading route, run keyboard and touch, then inspect the reduced and narrow views. If the figure loses its comparison at narrow width, change its composition before adding another control.
