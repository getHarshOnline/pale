# Agent surfaces and host checks

Pale generates repository guidance, hook contributions and selected tool-server descriptions from a project profile. This maintainer specification explains the identities and checks needed to install them and connect native host events to Pale operations. Several local components exist, but ordinary authenticated host admission and complete resident enforcement remain unfinished. Use the [workspace guide](../workspace.md) for available commands and the [MCP guide](../../interfaces/mcp/README.md) for its working transport.

## Keep the portable profile separate from its machine instance

The effective project profile contains selected Packages, roles, run policy, paths and capabilities, with no machine path or provider ID. Its digest identifies that portable configuration. The resolved project instance adds absolute paths, terminal and provider executables, generated files, runtime identity, session and evidence stores, causal-history stores and preferences. Changing only a machine path changes the instance digest, not the profile digest.

The surface manifest lists generated files. A surface plan covers repository-surface mutations; a materialisation plan covers the entire machine-local transaction. Every public mutation consumes an exact saved plan equal to a freshly recomputed plan before the first write. A portable plan records the declared reading order even when a required file is missing. Machine verification checks the source's authority; what the recipient actually read is a separate observation.

The one-shot CLI and standalone MCP render the portable profile. A required host command can remain blocked there despite having a declared binding. [Machine resolution](../../crates/pale-application/src/compile/machine_resolution.rs) checks the selected Pale and terminal executable identities before rendering the exact repository command under its bound host tool.

## Carry both tool names through every representation

The name advertised to the model and the name in a host lifecycle event can differ. In the observed Codex combination, the callable was `exec_command` and the `PreToolUse` event named `Bash`. The [operation contract](../../crates/pale-core/src/records/operation_contract.rs) keeps `model_name` separate from the native `name`: rendering uses the former, hook matching the latter.

Preserve both fields through declarations, schemas, generated language bindings and operation checks. An earlier Go decode/write path lost `model_name`; the operation seal rejected the loss while structural validation alone accepted a stripped authored declaration. The regenerated projections preserve both. Qualifying a provider mapping must also reject an unknown event, a changed command or a different tool-use identity. A successful render checks only one part of this path.

For a direct command, check its inputs, output and refusal cases. For the host path, additionally read back the advertised tool and native event, join that occurrence to the admitted session and operation, then recover its result and settlement. Private provider configuration, failure observations and resident session admission remain separate work.

## Install and retire only the owned contribution

Both native hosts use one repository entry, `AGENTS.md`. Source guidance owns a separate marked contribution per host; runtime rendering seals one shared entry containing the selected hosts' paths. Skills and references remain in their native layouts. Independent project or upstream Claude instructions are preserved. The [guidance starter](../examples/guidance-workspace/README.md#load-the-shared-entry-in-claude-code) owns the loading setting and reviewed migration from an earlier Pale contribution in `CLAUDE.md`.

On 16 November 2026 (UTC), Codex `0.169.0-alpha.11.1` loaded the complete installed shared entry. Claude Code `2.1.325`, with the explicit shared-file setting, loaded both hosts' Pale guidance contributions, the project marker and the independent Claude instructions, while omitting HTML comments. These observations establish instruction loading on those versions and settings; use of linked methods, authenticated runtime admission and host enforcement still need their own checks. Recheck loading when the host or its configuration changes.

The filesystem adapter compares the repository ownership record with the machine's separate installation history, validates staged bytes against the plan digest, and treats symlinks, non-regular files and malformed surfaces as collisions. Explicit adoption uses the [workspace command's plan and apply flags](../workspace.md).

[Surface status](../../sdk/rust/src/local/materialization.rs) compares actual bytes and permissions, hashing either the whole generated file or its owned block. It reports drift without changing the checkout. The [mutation tests](../../interfaces/cli/tests/mutation.rs) cover missing or changed generated files, changed permissions, edited or incomplete managed blocks, and unchanged status when only surrounding user text changes. Apply performs its own ownership checks.

A current surface can show no drift while an older managed block survives beside it. Trace predecessor entries across the selected host scopes and rehearse retirement against the exact baseline, including preservation and restoration. The [workspace maintenance method](../../packages/agent-work/workspace.md) covers those checks.

[Settlement](../../crates/pale-application/src/plan/result/settlement.rs) rolls back an attempt when receipt absence or collision is confirmed. Uncertain publication retains the exact attempt for reconciliation. Test the distinction with the [receipt commit method](../../packages/architecture/release.md).

Classify generated files individually. Portable skills, guidance, indexes and contracts may be committable; activation, sealed context, locks and receipts are machine-bound. The `.pale/` tree contains both. Applying surfaces grants no Git authorisation.

## Merge hooks into the repository's existing configuration

Compilation projects only Pale's handler contribution, sealing its inert intent and runnable bytes under `.pale/hooks/<harness>/`. Activation structurally merges that handler into the repository's existing `.claude/settings.json`, or its selected Codex source: `.codex/hooks.json` or inline hooks in `.codex/config.toml`.

Preserve every unrelated key, matcher group and handler. Never create a second Codex hook source; if both forms exist, stop for an explicit choice. Removal takes out exactly Pale's handler. Global configuration in `~/.claude`, `~/.codex` and `~/.gt`, `settings.local.json` and ambient activation remain outside this operation. The [native hook merge law](../../crates/pale-application/docs/math/native-hook-merge.display.tex) specifies the composition.

The static hook route names only the event, workspace, repository and exact provider binding with its identity. The executable can separately select a protected hook connection with [`--resident-hook-config`](../../interfaces/cli/README.md); that local selection is not part of the route sent to the resident. At the event, the resident resolves the live generation, path, policy, context and session. Those changing facts must not be frozen into the repository's command.

## Register the selected tool catalog separately

The [renderer](../../crates/pale-application/src/render/shared_artifacts/discovery.rs) seals a host fragment under `.pale/tools/<harness>/` and a separate catalog at `.pale/tools/<harness>/native-actions.json`. It includes the selected catalog and input schema beside an inert `pale-mcp` fragment.

Registration needs a separate authorised structural edit to the repository's `.mcp.json` or `.codex/config.toml`. Bind the pre-edit bytes, preserve unrelated servers and settings, reject concurrent changes and verify read-back. Retirement of an earlier shared catalog must use its installation ownership records and preserve restoration of the predecessor bytes and modes.

The ordinary [standalone executable](../../interfaces/mcp/src/lib.rs) exposes the complete request-local command set. A production launcher still needs to verify and accept the exact selected catalog, schema and executable and expose only its selected pure actions. Host-specific NativeRust selection, production registration and bootstrap retirement remain unfinished. Disposable launcher and structural-edit fixtures do not supply that production path.

MCP protocol compatibility is implemented separately. The [protocol adapter](../../interfaces/mcp/src/protocol.rs) supports initialized clients and self-contained requests; the [MCP guide](../../interfaces/mcp/README.md) owns revisions, negotiation, metadata and examples. [Lifecycle tests](../../interfaces/mcp/tests/protocol/lifecycle.rs) exercise negotiated fallback, duplicate initialization, malformed metadata and independent stateless requests. A connected server and a callable tool establish neither model judgment nor live resident admission. Schema-format warnings and installed-product qualification still require attention.

Captured resident and review fixtures are generated by their application or SDK owners. Keep schema, Package, profile and instance digests consistent with those sources; preserve validation, refusal cases and exact-result assertions when regenerating. Passing those consumers does not establish host registration or ordinary session admission.

## Join native completion to the original call

Native completion can arrive through a different interface from the pre-tool hook. The observed Codex CLI streams omitted successful terminal evidence, while app-server command items supplied typed exits. Joining those channels requires the actual session, turn, tool-call identity, command and working directory, followed by verification of the provider's identity and permission and a link to Pale's saved root or child operation. Trusting each hook separately does not create this authenticated mapping.

The [completion reader](../../crates/pale-application/src/resident/hook/codex_completion.rs) checks captured Codex v2 start/completion notifications against the original pre-tool event. The [Rust SDK](../../sdk/rust/README.md) exposes `observe_codex_command_completion`. It requires matching session, turn, tool-use identity and reported cwd, preserves native item status separately from an optional typed process exit, and rejects changed native command metadata.

Keep the original hook command and the shell-wrapped native command as separate identities. Best-effort command actions prove no equivalence. The reader accepts the retained real zero-exit pair and rejects a changed turn. Its synthetic cases cover nonzero and missing exits, malformed phases and duplicate keys. It contacts no host, authenticates no carrier, registers no durable operation and consumes no invocation. Its report cannot close operation mapping or command equivalence.

The [SDK completion tests](../../sdk/rust/tests/resident_hook.rs) cover typed success and failure exits, absent exits for each terminal state, separate command identities, correlation mismatches, malformed phases, duplicate keys and the input-size bound.

## Bind each consequential event to permission

Keep session admission, narrower operation leases, temporary expiring hook state and persistent project continuity separate. Every consequential hook event, including a permission request, must use the session lease before the operation lease narrows it further.

Use the harness's native tool-use identifier as the per-invocation identity, stored as a digest. Preserve parallel registration, replay rejection, one-shot consumption and payload-mismatch checks. Child selection distinguishes a missing agent type, an empty selector, an unknown child class and an unobserved actor. Explicitly bind the native occurrence, active one-shot lease, durable operation lease and handle, policy decision, emitted denial and host-enforcement observation. Never choose the newest or first operation as a substitute for correlation.

The application can recover the host-identified session, recheck its saved lease against current permissions, and verify workspace, repository, path and provider. It can evaluate the selected pre-tool write policy under that session's write ceiling. The resident hook turn invokes these checks for a correlated occurrence. The production host integration still needs to supply its independent authorities and enforce the answer before the write.

The [authenticated hook request](../../crates/pale-application/src/resident/hook/frame.rs) captures the verified caller key after reading the frame and decodes its event from those exact bytes. Its session binding rejects a different caller, native activity, lease or grant. The resident listener preserves the current hook-admission result: rejected input, replay conflict, denied admission, missing configuration or unavailable protected recovery. With explicit response inputs, the [resident hook turn](../../crates/pale-application/src/resident/process_host/native_hook_turn.rs) continues the admitted operation through response preparation and release. Without those inputs or a selected handler, it refuses the request. The SDK exposes a prepared response only after its independent response authority admits and consumes the exact occurrence; hook-only attachments have no such authority. Replay or recovery uncertainty requires reconciliation. The older one-shot invocation registry cannot supply a resident grant, and a write policy finding no violation cannot become an Allow response.

The [native start body](../../crates/pale-core/src/records/native_tool.rs) preserves the exact event bytes and contribution route inside the caller-signed common request. The [SDK producer](../../sdk/rust/src/resident_hook/native_start.rs) prepares this body for an independently supplied signer and rejects a substituted body before opening a connection. The actual resident start path requires the transport's verified key to belong to that signed caller; signature verification or a matching operating-system user alone cannot establish this association. The service's caller-key admission defaults to refusal until its owner supplies that association from admitted key records.

The [native start owner](../../crates/pale-application/src/resident/process_host/native_hook_start.rs) reserves the authenticated occurrence under the current session before allocation and registers the actual durable start result. The policy's native invocation identity must match the signed event. Pending starts retain their original caller key through interrupted custody, and an exact start replay cannot replace a registered operation or clear its consumed state. The [program tests](../../crates/pale-application/tests/internal/resident/process_host/program_native_start.rs) exercise frame admission and durable start with declared signing and storage models; they do not establish a running host integration or native enforcement.

The [resident operation registry](../../crates/pale-application/src/resident/hook/operation_registry.rs) matches the authenticated caller, native activity, turn, tool-use identity and original event digest, then rechecks the exact session and operation lease before one-shot consumption. Its bounded entries preserve parallel calls and retain consumed occurrences until session expiry; they never evict a live call to admit another. The resident hook turn connects this process-local correlation to current operation recovery and retains the response continuation after consumption. The registry alone supplies neither durable replay evidence nor effect permission; reconstruction of a live registration after host restart remains a separate deployment responsibility.

The correlated event can then be checked against the operation's [compiled native-tool mapping](../../crates/pale-application/src/resident/hook/operation_registry/tool_binding.rs). Exactly one capability requirement must match the route's provider, native tool name, typed input and command constraints, within the operation lease's capability and effect limits and for the capability in the issued handle's original request. A broader lease cannot substitute another capability for that request. A model-facing alias, unavailable provider, unexpanded command source or ambiguous requirement cannot supply that match. Its write-policy selection intersects the session's write authority with that unique capability inside the operation lease, so a broader session cannot supply a write effect missing from the operation. Finding no write-boundary violation still grants no effect permission and does not establish current operation progress. A production host integration that supplies the already-issued operation and registers its authenticated event remains missing, so a first-seen tool-use ID stays blocked.

Current progress needs the operation's protected history and another check before its next transition. The issued handle's initial observation is not current state, and [observation recovery](../../crates/pale-application/src/resident/operation_observation_custody/recovery.rs) establishes anchored history without promising that its head remains latest at return. The existing [dispatch custody check](../../crates/pale-application/src/resident/operation_dispatch/recovery.rs) re-reads the actual operation head, its checkpoint, the current checkpoint and the independent anchor; a subsequent transition still needs a commit against its exact predecessor. The hook now uses that custody check before preparing its response. The [response owner](../../crates/pale-application/src/resident/operation_dispatch/hook_response.rs) retains the exact output and its permission and disclosure references, then commits preparation and dispatch observations with their checkpoints. It rechecks current authority, output equality, disclosure and dispatch custody before returning the frame once. The deployment must explicitly supply the [permission and disclosure authority](../../crates/pale-application/src/resident/hook/response_policy.rs), signing inputs, recovery inputs and bounds; no production authority is selected by default. The existing [provider attempt owner](../../crates/pale-application/src/resident/operation_dispatch/selection.rs) supports Compute, so a `HostNative` declaration alone still cannot turn that path into write enforcement.

[Response recovery](../../crates/pale-application/src/resident/operation_dispatch/hook_response/recovery.rs) can reconstruct prepared or dispatched output from protected history, including after the original leases expire. That result is historical evidence, not a releasable frame, renewed permission or proof of emission. Deployment integration must reconcile interrupted response delivery without recreating a live occurrence or retrying a possibly emitted answer.

Denial evidence distinguishes policy selection, the response attempt and the host's acknowledgement of prevention. The [decision ledger](../../crates/pale-application/src/decision_evidence/current.rs) represents the observable target, native occurrence and operation binding, and links each later stage to its predecessor. Failed or uncertain emission remains explicit. These structural checks do not authenticate the source, establish current permission or prove durable retention and recovery. The ordinary host path must admit and recover each transition and independently establish host enforcement; a selected denial or emitted response cannot supply that proof.

[Completion admission](../../crates/pale-application/src/operation_admission/tool/mod.rs) checks the original provider binding before consuming an invocation. The [correlation regression](../../crates/pale-application/tests/operation_admission_cases/correlation.rs) rejects a substitute provider while leaving the original able to finish exactly once. The occurrence digest alone cannot replace that comparison; the durable host path must preserve it.

Ordinary work must remain blocked while Pale is unavailable. One-shot execution is an explicit diagnosis, recovery and comparison tool. Without an explicit hook configuration, the ordinary executable reports an unavailable resident carrier. A configured executable or an embedded CLI with a hook or operation attachment can send the original event. The resident preserves admission refusals and can return prepared output when its explicit response inputs pass the application checks. The ordinary executable’s hook-only configuration cannot release that output because it supplies no independent response authority. An embedder must supply that authority separately. The SDK rejects unadmitted, malformed and late replies without a retry. Denial still needs end-to-end enforcement in each host. At the public command boundary, a wrong runtime digest, context digest, repository identity or substituted opposite route produces a structured denial on both harnesses.

## Recheck the host behaviour on the selected version

Earlier documentation and code inspection supplied the following design constraints. They are requirements to verify against the pinned host before relying on them, not results of a fresh host run or a promise about every version or tool path.

- Claude Code supported explicit structured denial from a successful HTTP, MCP-tool, prompt, agent or command handler. Codex ran command handlers, parsed but skipped prompt and agent handlers, and had no asynchronous command hooks. The common deterministic denial was a local command emitting exit code 2 or a supported structured denial. Exit code 1 was a hook failure that allowed the call; the most restrictive decision across settings scopes prevailed.
- An unreachable HTTP backend was a non-blocking error. A killed, crashed or timed-out command cannot emit its denial. Use the host's operating-system confinement for filesystem and network access, including child processes, as the independent limit beneath hooks; qualify its actual configuration and bypasses.
- Codex trusted a hook definition by hash and skipped changed definitions pending renewed trust. Hosted tool paths could bypass hooks and some paths could opt out. Its operating-system confinement and static command rules therefore remained the base restrictions, with hooks adding policy interpretation.
- Neither documented hook payload supplied token or context usage. Metering is external and advisory. Injected context was capped and could be replayed from the transcript on resume; pass references that can be resolved again instead of treating old injected state as current.

Pale's persisted session record is limited to 1 MiB and rewritten under a lock. It holds bounded session context; an invocation stream belongs in its own append-shaped evidence store. A generic adapter's dispatch receipt establishes the exchange. An orchestrator's launch receipt establishes the child run; the owner's outcome is a further observation. Native wait and cancellation evidence belong to that execution provider.

## Measure session and compaction costs

The hook overhead target is less than one millisecond per tool call because a query can make about a hundred calls. Measure process startup, file access, parsing and blocking work, not only the handler body. Prefer a small native path and asynchronous work where supported, while completing permission checks before their actions.

The current compaction path re-injects the whole startup guidance without measuring its size and arms a refresh without establishing whether the host retains its session identifier. A changed identifier can return a session to defaults. Measure both identifier and payload, state which continuity facts are reasserted, and compare cold and warm percentiles with session start.

Measure cache reads and creation across multiple worktrees on the pinned hosts before changing prompt layout. Earlier observations treated machine and directory as part of the cache key; moving changing sections outside the cached prefix made one reported case worse because that block grew. That report does not qualify the current host.
