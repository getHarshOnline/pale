# Split work and brief the people doing it

Delegate when distinct judgments or separate pieces of work will improve the result enough to justify joining them again. Keep tightly coupled reasoning with one worker. Use the caller's permission for delegation and the tools the current host actually provides.

## Give each part an outcome and an owner

Start from the original request, corrections, settled context and existing task record. Name the outcome, who decides, permitted reads and changes, current inputs, how the result will be checked and who will integrate it. Split by independently checkable outcomes, not equal workloads. Each recipient needs its sources, write scope, expected result, consumer and return condition. Add a budget or separate record when the task needs one; an ordinary handoff needs no new dossier.

Choose how the parts can proceed:

| Relationship | How to work |
| --- | --- |
| Independent | Work in parallel, then combine the results. |
| Shared reading | Read the same identified source version. |
| Separate writing | Give each file one writer. |
| Ordered | Finish the input before its consumer uses it. |
| Preparation before integration | Prepare independently; combine only when the common prerequisite is ready. |
| Shared state or risk | Take turns. |

Urgency leaves those dependencies intact. Several readers can judge the same source independently; two writers changing it at once need coordination.

## Use the smallest useful team

Choose readers for separate research or review questions, writers for disjoint artifacts, and ordered waves where one result feeds another. Separate a creator from an evaluator when judging one's own work would undermine the required independence. Each specialist should contribute a judgment the others do not already supply.

For substantial work across products or subjects, give each subject an owner who reads its sources and follows its full task or reader journey. A critic can examine shared questions such as language, structure, correctness or navigation and send findings against named sources to that owner. The critic does not become another writer on the same files. Keep one integrator responsible for dependencies and the combined result, rather than asking one worker to understand and rewrite the whole suite.

A brief carries the original request, material corrections, existing approvals, goal, settled choices, relevant owner pages and code paths, exclusions, unresolved dependencies and what done means. Point to the applicable shared rules instead of restating them. Brief the worker to continue to the agreed result, without invented stop points or reports after every step. Choose the return form for the consumer; require a schema only when it will be read as data. A file count or worker count says nothing about reading or quality. Review the source use, reasoning, changes and actual result.

## Check that the assigned worker actually starts

When a named specialist or separate reviewer is required, inspect the host's dispatch tool and role mapping. Confirm that the intended worker started with the brief; an accepted request or registered role only shows that dispatch was requested. Put a failed start or substitution in the task's existing handoff or reply, so the integrator knows which work is still missing.

Use a generic reviewer only when substitution is permitted and the host can start a separate worker with the same input version, criteria and permissions. Check any required independence from the actual review conditions. If that cannot be done, name the missing capability and leave that review unfinished while other authorised work continues.

## Join the results once

First check that each result used the agreed sources and version and stayed within its write scope. Then assess its substance against the task's completion criteria. Reject stale or widened work, preserve useful dissent, resolve conflicts explicitly and check the combined result. Separate local passes do not check how their changes work together.

Return the useful result, its supporting evidence, unresolved disagreements and the next handoff where the task already lives. Use a graph only when it makes the dependencies easier to understand. Stop or serialize the affected branch when permissions are unclear, writes overlap, inputs change, a result cannot be checked, no integrator exists or coordination costs more than it saves. Continue independent work.
