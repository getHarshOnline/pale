# Check an image workflow from request to export

For creating or correcting the asset itself, use [Make an asset that belongs in its destination](assets.md). For a generator choice or defect, follow [Choose and diagnose a generation method](generate.md). Use this method to check whether the application can produce the requested image and deliver the right export.

## Identify the brief and what each source supplies

Choose one intended use and destination. Read the accepted brief, creative direction and corrections with the source owner. State what the image must preserve, what may change, and which claims it depicts. Resolve each source by owner, revision or digest and declared role. Preserve source identity across reference study, generation, refinement and export. Check permitted uses separately for conditioning, retained context, model adaptation and distribution. Assess byte integrity, authenticity, permission for this role and fitness for the brief separately. A matching digest establishes integrity against the selected record. Ask the relevant owner to confirm identity, permitted use and suitability where those remain open.

For a refinement, identify the source frame and the features the treatment must preserve. Mark which transformations may change composition, identity, geometry or palette. If a source or treatment is unavailable, return to the owner before substituting it. A text-only fallback changes the production route and needs the brief's explicit allowance.

## Check one run in the application that produces it

Identify the selected workflow, engine, models, node set, environment, inputs, parameter and seed policy and output limits. Identify the actual execution surface and the owner of credentials, source custody, staging and cancellation. Keep native credentials out of prompts, files, logs and receipts. A proposed or validated workflow can have no runnable provider. Inspect the actual model and input references and require a permitted route before any effect. Before running, check the current rights, brief and required owner facts against their owning records. If permission has expired or been withdrawn, or a necessary fact cannot be established, leave that input unused. Check a replacement for the same intended use.

Use isolated, synthetic or rights-cleared inputs to exercise preflight and the request-to-receipt path. Include changed source bytes, an unavailable or ambiguous model, a failed or interrupted run, and partial output acquisition. A dry run proves the checks it reaches. On the native route, preserve the submitted graph or equivalent request, resolved inputs, recorded seed, output identities, failure state and any retry lineage. Verify the actual outputs from the receipt. Separate reproducible inputs from an observed reproduction and declare nondeterministic steps or allowed variation.

When the runner can retry or cancel, verify the exact run identity and native read-back under an uncertain response or a race with completion. Rehearse restart, removal of runtime state and replacement of a provider against the required custody. The owning application defines the request, effect and recovery contracts and owns its native records.

## Carry the reviewed output to its destination

Keep the workflow definition, accepted request, run receipt, human asset review and export receipt as separate evidence, using the owner's schemas. The reviewer sees the exact output and original source roles. Record craft, factual fidelity, rights, disclosure and destination as separate checks. Refer factual claims, catalogue state, canon or likeness authority to the appropriate owner. A run result does not change them.

Bind each export to the approved review, exact derivative, destination and required disclosure. Use the native export path and inspect the exact derivative for embedded prompts, graphs, source identifiers or other metadata beyond the destination's permitted fields. Preserve the original and internal provenance under their retention rules. Check the derivative again after stripping or re-encoding, and bind the verified bytes to the export record with the required disclosure.

Recheck the review and its applicable upstream authorities before export. If a source, permission, depicted fact or approval is withdrawn or replaced, block dependent future runs or exports and flag retained outputs for owner review. Keep unrelated outputs on their own evidence. Publication requires its own native decision and read-back.

Keep requests, run IDs, outputs and recovery history in the application’s existing production records. Put the review and export result there or in the requested reply; do not create a separate account of the agent’s work.

For a production review, assess the proposed workflow or exact saved output with the independent design review method. If the route cannot run, identify its missing prerequisite and continue the checks the supplied material supports. Compare the actual run record with the output, and judge the image against its source roles and intended placement. State which conclusion remains open when independent review or application read-back is unavailable. Return the exact candidate, checks run, observations and unrun checks in the existing production record or reply, carrying forward existing approval and identifying any remaining owner decision for execution, export or publication.

## Before handing off

- [ ] Does the reviewed candidate correspond to the supplied source roles and production inputs?
- [ ] Does the run record identify the actual output, with any uncertain result left open?
- [ ] Does the exported image work in its intended placement?
